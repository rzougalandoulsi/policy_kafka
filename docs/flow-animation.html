Governance flow explainer

How a manifest travels from the client through Governance, OPA and the two Kafka protocol topics to the Orchestrator, and back. Pick a scenario, press play, or step through with ← → and space.

Request status —

Steps

    • HTTP (REST API)
    • OPA decision call
    • requests.manifest command
    • response.manifest event
    • existing topics (teams.changes, request.status)
    • internal step (same DB transaction)
    • missing or failed reply

    Invariants that hold in every scenario

    • Exactly two topics carry the Governance ↔ Orchestrator protocol: requests.manifest (commands SUBMIT_MANIFEST, AUTHORIZE_PLAN, REJECT_PLAN) and response.manifest (events PLAN_PROPOSED, MANIFEST_COMPLETED, MANIFEST_FAILED, MANIFEST_REJECTED).
    • Every status transition is checked by RequestLifecycle and appended to request_status_history; commands leave through a transactional outbox, events arrive through an inbox keyed by eventId.
    • Decision precedence is HARD_DENY > DENY > REQUIRE_APPROVAL > ALLOW. Only bypassable violations honour exceptions, and only exceptions Governance itself resolved. Approval requirements are never bypassable.
    • The Orchestrator releases Actions only after verifying decisionId + planId + planDigest + stateVersion. A plan computed against an older stateVersion ends as STALE_PLAN.
    • OPA unreachable, bundle revision mismatch or a Java/Rego disagreement all yield ERROR: nothing is published and the API answers 503.
